# MDShare 设计方案

## 产品目标

打造一个极简、匿名、移动端友好的 Markdown 快速分享服务。

核心理念：
- 链接即内容
- 无需注册即可创建和访问
- 默认临时、默认轻量、默认低干扰
- 在创建前即可编辑并实时预览

适合的核心场景：
- 临时分享说明文档、日报、会议纪要、日志片段
- 在手机上快速粘贴 Markdown 并立即生成可访问链接
- 在 PC 上边编辑边预览，然后一键生成分享链接
- 小范围协作修改同一份 Markdown 内容

## 需求冲突与推荐收敛

你的想法里有几组天然冲突，需要先定清楚产品边界。

### 1. 无登录 vs 可继续管理分享

推荐方案：不做账号系统，改用“匿名所有者令牌”。

做法：
- 创建分享后生成两个能力不同的链接
- 访问链接：给读者看内容
- 管理链接：给创建者自己改内容、延长有效期、删除分享

这样既保留“无需注册”，又不牺牲后续管理能力。管理链接默认只在创建成功页展示，并缓存在当前设备本地。

### 2. 可编辑分享 vs 安全性

推荐方案：默认只读，不把“任何拿到链接的人都可编辑”作为默认行为。

做法：
- 默认生成只读访问链接
- 如果开启“允许编辑”，额外生成一个编辑链接
- 访问链接和编辑链接分离

这比单链接同时具备查看和编辑能力更安全，也更符合“轻量分享工具”的心智。

### 3. 阅后即焚 vs 链接预览机器人

推荐方案：不要把“首次请求页面”直接判定为已阅读，而是采用“确认查看后销毁”。

做法：
- 对开启阅后即焚的链接，先展示提示页
- 用户点击“查看内容”后才算真正阅读
- 支持两种焚毁语义：
  - 推荐默认：首次查看后 10 分钟销毁
  - 高级选项：首次查看后立即失效

这样可以避免微信、Slack、搜索爬虫、社交平台预览机器人误触发销毁。

### 4. 极简产品 vs 实时协作复杂度

推荐方案：产品层面保留“可协作编辑”，但技术实现分阶段。

做法：
- 第一阶段：支持多人进入同一个编辑链接，内容自动保存，后写覆盖前写
- 第二阶段：升级为真正的 CRDT 实时协作，支持光标/在线状态/更平滑的冲突合并

这样可以先把核心价值跑通，而不是一开始被协作内核拖慢上线。

## 推荐 MVP 范围

第一版建议只做这些：
- 匿名创建 Markdown 分享
- 粘贴内容或上传 `.md` / `.txt`
- PC 端编辑区 + 实时预览双栏
- 移动端编辑/预览双 Tab
- 到期时间设置
- 密码访问
- 阅后即焚
- 只读链接
- 可编辑链接
- 管理链接
- 短链接访问

第一版先不做这些：
- 用户注册登录
- 评论
- 富文本编辑器
- 永久历史版本
- 团队空间
- 搜索公开内容
- 复杂权限体系

## 用户体验设计

## 首页 `/`

首页就是编辑器，不先讲故事，不先引导注册。

页面结构：
- 顶部：产品名、一个简短副标题、主题切换
- 主区域：
  - 左侧为 Markdown 编辑器
  - 右侧为实时预览
- 底部或右上角：分享设置折叠面板
- 主按钮：`创建分享链接`

推荐默认文案：
- 标题：`贴上 Markdown，立刻分享`
- 副标题：`无需登录，生成短链接，可设密码、过期和编辑权限`

交互细节：
- 进入页面自动聚焦编辑器
- 支持粘贴 Markdown
- 支持拖拽上传 `.md` / `.txt`
- 未创建前的内容自动保存在本地草稿
- 草稿按浏览器本地存储保存，避免误刷新丢失

### PC 端体验

PC 端采用左右分栏：
- 左边编辑
- 右边预览

编辑时实时渲染，滚动联动不是必须，但可以作为增强项。

### 移动端体验

移动端不要强行双栏，改成两个切换页签：
- 编辑
- 预览

分享设置放入底部抽屉或折叠卡片，避免页面过长。

## 分享设置

默认只露出最关键的 4 项，避免吓到用户。

### 1. 有效期

推荐快捷选项：
- 1 小时
- 1 天
- 7 天
- 30 天

推荐默认值：`7 天`

理由：
- 比 24 小时更宽松，减少“链接刚发出去就过期”
- 又不会无限占用存储

### 2. 访问密码

默认关闭。

开启后：
- 访问者需要先输入密码
- 密码只做校验，不回显原文

### 3. 阅后即焚

默认关闭。

开启后推荐提供两个子选项：
- `首次查看后 10 分钟销毁`（推荐）
- `首次查看后立即失效`

### 4. 编辑权限

推荐选项：
- `只读`
- `持有编辑链接者可编辑`

第一版不建议开放“持有访问链接也可编辑”。

## 创建成功后的体验

点击创建后进入成功状态卡片，而不是直接跳走。

成功页应展示：
- 访问链接
- 编辑链接（如果启用）
- 管理链接
- 到期时间
- 当前权限摘要

操作按钮：
- 复制访问链接
- 复制编辑链接
- 打开预览
- 继续编辑

友好提示：
- `请保存管理链接；没有账号体系时，它就是你后续修改和删除这份内容的唯一凭证之一。`

如果当前设备可安全缓存管理能力，也可以提示：
- `本设备已为你保存管理权限，可稍后回来继续修改。`

## 公开访问页 `/s/[slug]`

访问页要极简，避免像博客系统。

展示内容：
- Markdown 渲染结果
- 简单元信息：创建时间、剩余有效期
- 如果需要密码，先展示密码输入页
- 如果是阅后即焚，先展示确认查看页

不要展示的东西：
- 作者信息
- 平台社区入口
- 推荐内容
- 干扰型导航

如果链接已过期或已销毁：
- 明确提示“该分享已失效”
- 不返回模糊错误

## 编辑/管理页 `/e/[slug]`

如果用户持有编辑令牌或管理令牌，进入编辑页。

能力包括：
- 改 Markdown 内容
- 调整有效期
- 开关密码
- 开关阅后即焚
- 删除分享

第一版建议：
- 管理能力包含编辑能力
- 编辑能力不一定包含删除能力

也可以在内部仍使用同一种管理令牌，只是在 UI 上区分“编辑链接”和“管理链接”的展示方式。

## 链接模型

推荐采用三种链接能力模型：

### 1. 访问链接

示例：
`/s/Ab3kPq9x`

能力：
- 只读访问
- 如果启用密码，需要先输入密码

### 2. 编辑链接

示例：
`/e/Ab3kPq9x#edit=TOKEN`

能力：
- 查看
- 编辑
- 参与协作

### 3. 管理链接

示例：
`/e/Ab3kPq9x#manage=TOKEN`

能力：
- 编辑
- 修改设置
- 删除

推荐把敏感令牌放在 URL Fragment 中，而不是 Query 参数中。这样令牌不会自然出现在大多数服务端访问日志里，泄露风险更低。

## 信息架构与页面清单

- `/`
  - 创建页
- `/s/[slug]`
  - 公共访问页
- `/e/[slug]`
  - 编辑/管理页
- `/api/shares`
  - 创建分享
- `/api/shares/[slug]`
  - 获取分享元数据/内容
- `/api/shares/[slug]/access`
  - 密码校验、阅后确认
- `/api/shares/[slug]/update`
  - 编辑内容
- `/api/shares/[slug]/settings`
  - 修改过期时间、密码、焚毁策略
- `/api/shares/[slug]/delete`
  - 删除分享

## 技术方案建议

## 前端

推荐技术栈：
- Next.js App Router
- TypeScript
- Tailwind CSS
- CodeMirror 6 作为 Markdown 编辑器
- `react-markdown` + `remark-gfm` + `rehype-sanitize` 做渲染

为什么不用富文本编辑器：
- 你的核心是 Markdown 分享，不是文档协作平台
- 文本域 + Markdown 预览更贴合“链接即内容”的轻量感
- 更容易支持上传原始 Markdown 与原文编辑

## 后端

推荐架构：
- Next.js Route Handlers 负责 API
- PostgreSQL 负责持久化
- Redis 负责限流与短期状态

推荐部署组合：
- Vercel 部署 Next.js
- Neon 或 Supabase 托管 PostgreSQL
- Upstash Redis 做限流

这是当前阶段最省心的一体化方案，复杂度和成本都比较友好。

## 实时协作

推荐分阶段：

### 第一阶段

先实现：
- 多人可进入同一编辑链接
- 自动保存
- 最近修改会同步刷新

可以接受：
- 短时间内仍有覆盖写风险

### 第二阶段

引入真正的实时协作层：
- Yjs
- PartyKit 或 Hocuspocus
- CodeMirror 协作绑定

这样能获得：
- 冲突自动合并
- 在线状态
- 光标同步

如果你希望第一版就主打“多人同时改文档”，那就直接上 Yjs；如果你希望尽快上线验证需求，建议先做第一阶段。

## 数据模型建议

### `shares`

- `id`
- `slug`
- `markdown_content`
- `title` 可空
- `expires_at`
- `password_hash` 可空
- `editable_mode` 枚举：`read_only` / `edit_link`
- `burn_mode` 枚举：`off` / `after_first_view_grace` / `after_first_view_instant`
- `burned_at` 可空
- `first_viewed_at` 可空
- `owner_token_hash`
- `editor_token_hash` 可空
- `created_at`
- `updated_at`
- `deleted_at` 可空

### `share_views`

- `id`
- `share_id`
- `viewed_at`
- `ip_hash`
- `ua_hash`
- `confirmed` 布尔值

这个表主要用于：
- 判断“首次确认查看”
- 审计异常访问
- 支撑焚毁逻辑

### `share_revisions`（可选）

第一版可以不做。

如果你后面需要：
- 简单撤销
- 回滚误改
- 协作历史

再补这个表更合适。

## 关键安全与风控策略

匿名分享服务天然会遇到滥用问题，这一部分第一版就要做。

必须做：
- IP 级限流
- 单文档大小限制，推荐 `512 KB` 到 `1 MB`
- 上传仅接收文本类文件
- Markdown 渲染严格做 HTML 清洗
- 默认禁止搜索引擎索引
- 敏感令牌仅存哈希
- 所有链接强制 HTTPS

推荐做：
- 单 IP 每小时创建次数限制
- 异常峰值时触发验证码
- 黑名单关键词或滥用巡检任务

## 非功能性要求

### 性能

- 首屏可交互时间小于 2 秒
- 公共查看页服务端渲染
- 常规文档打开时间小于 1 秒

### 容量

- MVP 先限制单文档大小
- 不支持附件上传
- Markdown 内容直接存数据库

### 可用性

- 目标可用性 99.9%
- 过期清理任务至少每小时执行一次

### 维护性

- 单体 Next.js 应用优先
- 不拆微服务
- 协作服务只有在第二阶段再单独引入

## 最合理的产品默认值

如果让我替你拍板，我建议默认值如下：

- 默认有效期：`7 天`
- 默认权限：`只读`
- 默认不设密码
- 默认不开启阅后即焚
- 创建成功后同时给出“访问链接”和“管理链接”
- 只有显式开启时才给出“编辑链接”
- PC 双栏编辑预览
- 移动端双 Tab 编辑预览

这些默认值兼顾了：
- 极简
- 安全
- 成功率
- 后续可演进空间

## 分阶段实现建议

### Phase 1：核心可用

- Next.js 基础框架
- 创建页
- 公共访问页
- 本地草稿
- 短链接
- 过期时间
- 密码访问

### Phase 2：匿名管理

- 管理令牌
- 编辑链接
- 设置修改
- 删除分享
- 失效页

### Phase 3：增强协作

- 多人同时编辑
- 基础 presence
- 自动刷新/同步

### Phase 4：正式实时协作

- Yjs 协作
- 冲突自动合并
- 光标同步
- 协作状态提示

## ADR 摘要

这份设计默认采用以下关键决策：
- 使用匿名所有者令牌代替账号体系
- 使用访问链接与编辑链接分离的权限模型
- 阅后即焚采用“确认查看后销毁”而非“首次请求即销毁”
- 产品先保持单体架构，实时协作按阶段引入

## 结论

这不是一个“在线 Markdown 平台”，而应该是一个：

`把 Markdown 变成临时链接的超轻量工具`

只要我们守住下面三点，这个产品体验就会很对：
- 打开就能写，不先登录
- 写完就能发，不学规则
- 发出去能控风险，不至于失控

如果继续往下做，我建议下一步直接进入：
- 页面结构与组件拆分
- 数据库 schema
- Next.js 项目初始化与第一版页面实现
